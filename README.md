# Stateful Coding Worker

Локальный MCP-сервер для корпоративного Kilo Code. Реализованы I0–I4:
stdio transport, text-only inference, долговечные сессии с выбранными снимками
исходников, кандидаты, review loop, проверка одобренного кандидата компиляцией,
локальный raw commit с Git hooks и postprocess отдельным коммитом. Рабочие
файлы проекта меняют только `candidate_apply` (целевой тестовый файл) и
`postprocess` (только пути raw-коммита). Push MCP не делает.

Нужны Node.js 24+ и npm. Подготовка и проверки:

```powershell
npm ci
npm run typecheck
npm test
```

Тесты используют локальный fake HTTP backend; реальных модельных запросов в
`npm test` нет. `npm test` также собирает TypeScript и проверяет stdio MCP.

Конфигурация — доверенные переменные окружения, не аргументы tool:

| Переменная | Назначение |
| --- | --- |
| `WORKER_BASE_URL` | Полный базовый URL API, включая `/v1` |
| `WORKER_MODEL` | Реальный идентификатор модели на этом endpoint |
| `HARNESS_MODEL_API_KEY` | Существующий ключ, передаваемый как Bearer |
| `WORKER_TIMEOUT_MS` | Таймаут подключения и чтения ответа; по умолчанию 60000 |
| `WORKER_TSCONFIG` | tsconfig по умолчанию для проверки кандидата, путь относительно корня проекта; в монорепе его выбирает оркестратор в `candidate_apply` |
| `WORKER_POSTPROCESS` | Необязательно: порядок и допустимый набор инструментов `postprocess` через запятую из `eslint`, `prettier`; по умолчанию `eslint,prettier` |

Корень проекта не настраивается: при запуске MCP берёт Git-репозиторий своего
рабочего каталога (`git rev-parse --show-toplevel`). Session tools работают
только внутри Git-репозитория; иначе они возвращают `configuration_error`, а
хранилище нигде не создаётся.

`worker_diagnostics({})` проверяет конфигурацию без inference и показывает
вычисленный `workspaceRoot` (или `workspaceError`).
`worker_instruct({ message })` делает ровно один запрос без tools и retries,
возвращает полный текст либо безопасную диагностику. Неполный ответ и попытка
tool call считаются ошибкой. Этот вызов не хранит диалог.

`session_start` создаёт сессию с 1–8 разрешёнными файлами (`allowedPaths`,
существующими или новыми) и необязательным `commitType` (`test`, `feat` или
`fix`, по умолчанию `test`), который станет префиксом raw-коммита.
`context_set` заменяет brief, acceptance criteria и снимки выбранных файлов,
увеличивая revision. Acceptance criteria обязательны: это согласованный ролью
список сценариев, по одному на пункт, и исполнитель реализует ровно его.
`worker_chat` делает один inference: текущий контекст, текущий запрос и, пока
нет кандидатов, только последний успешный обмен; вся история сохраняется.
`session_status` по умолчанию возвращает компактные счётчики и состояние.
`includeDetails: true` явно открывает полные brief, snapshots, turns и errors.

Существующие разрешённые файлы каждый ход целиком уходят исполнителю как
`targets` (без номеров строк) и учитываются в бюджете. `worker_chat` просит
один JSON-объект без Markdown:

```json
{"files":[
  {"path":"src/price.ts","edits":[{"search":"…","replace":"…"}]},
  {"path":"src/price.test.ts","content":"…полный файл…"}
]}
```

- Существующий файл — `edits` или полный `content`; новый — только `content`.
  Старый формат `{"path","content"}` тоже принимается.
- `search` — 1–12 целых строк из снимка, найденных ровно один раз. Сравнение
  точное, только концы строк нормализуются; нечёткого совпадения нет. Правки
  файла применяются по очереди и всегда к снимкам из `targets`, а не к прошлому
  кандидату.
- Файл в CRLF остаётся в CRLF, BOM сохраняется; файл со смешанными концами
  строк правками не меняется (только `content`).
- Заглушки (`...`, `// rest of the code`, `// existing code`) и номера строк
  отклоняются. Одно внешнее ограждение ```` ``` ```` вокруг всего ответа снимается.

Кандидат создаётся, только если применились все правки всех файлов. Тогда он
неизменяем: `candidateId`, итоговый код, снимки на момент генерации и
минимальный unified diff по каждому файлу. `worker_chat` сразу возвращает
`candidateId` и `artifacts [{path, content, edits?}]` — код готов к ревью без
`candidate_read`. Иначе кандидата нет: tool возвращает `responsePreview` и
`candidateDiagnostics` со всеми проблемами (код, файл, номер правки, подсказка:
«отличается только отступом», ближайшая строка и первое отличие, число
совпадений). Эти же проблемы автоматически уходят исполнителю в следующем
`worker_chat` как `previousReplyProblems`. Код не обрезается и не исправляется
сервером. Файл больше 192000 байт кандидатом не становится.

`candidate_apply` и `postprocess` работают с кандидатом целиком (этап F2): ниже
«целевой файл» означает каждый файл кандидата. Предусловия проверяются для
всех файлов и называют конкретные (`target_dirty`, `target_changed`,
`missing_directory`). Записываются и коммитятся только файлы, отличающиеся от
снимка. Typecheck должен включать каждый TypeScript-файл кандидата (`.json` и
другие — нет), ошибки оцениваются по всем его файлам. При неудаче каждый файл
откатывается по общему правилу, а неоткатываемые перечисляются в `conflict`.

`candidate_read` возвращает полный код и diff кандидата, его revision, текущую
revision и историю ревью; устаревший кандидат помечается `stale`. Он нужен для
старых версий, diff и чтения после рестарта, но не сразу после `worker_chat`.
`candidate_review` одобряет или отклоняет конкретный кандидат на текущей
revision и добавляет findings в историю. Устаревший или уже отклонённый
кандидат одобрить нельзя — нужна новая версия. Следующий `worker_chat`
получает текущий контекст, последний кандидат один раз и его findings, если
он отклонён; замечания к более старым версиям в prompt не попадают. Ни один
из этих tools не пишет в рабочие файлы проекта.

На I3 `candidate_apply` применяет одобренный кандидат текущей revision и
проверяет его компиляцией. До записи MCP требует, чтобы корень проекта был
корнем Git-репозитория, целевой файл не имел незакоммиченных изменений
(`target_dirty`) и совпадал со снимком на момент генерации, индекс был пуст
(`index_not_clean`), а снимки контекста не изменились. Иначе — `conflict` без
записи. Незастейдженные правки и неотслеживаемые файлы в других местах
разрешены и в коммит не попадают. Индекс должен быть пуст, потому что коммит
берёт его целиком, а hooks вроде lint-staged работают с застейдженными файлами.

Затем MCP записывает только целевой файл и запускает без shell `tsc`, ближайший
к выбранному tsconfig. Tsconfig — аргумент `tsconfig` в `candidate_apply`
(в монорепе — конфиг пакета целевого теста), иначе `WORKER_TSCONFIG`. Это путь
к `.json` внутри проекта, а не команда: по решению пользователя оркестратор
выбирает его сам, потому что пакетов много. Затем:
сначала `--listFilesOnly` проверяет, что целевой тест действительно входит в
программу, потом `--noEmit --incremental false --composite false`. Typecheck
без целевого файла — `error` `target_not_in_typecheck`, а не успешная проверка;
его можно повторить с другим tsconfig. Ключ модели в окружение
`tsc` и `git` не передаётся.

- `committed` — см. ниже raw commit.
- `validation_failed` — `tsc` нашёл ошибки в целевом файле; exit code, stdout и
  stderr (каждый поток не длиннее 8000 символов, обрезка помечена явно); файл
  восстановлен побайтно или удалён, если его не было.
- Ошибки `tsc` только в других файлах (старые ошибки монорепо, незаконченная
  работа) не мешают: в целевом файле ошибок нет, поэтому коммит создаётся, а
  в ответе есть `typecheck_errors_outside_target` с этими ошибками. Так
  засчитывается только провал с нормальной диагностикой `error TS…`; падение
  `tsc` без неё — повторяемый `typecheck_unrecognized`. Допущение: собственные
  ошибки теста `tsc` показывает в самом тесте, а не через глобальные
  аугментации в других файлах.
- `error` `typecheck_failed_with_uncommitted` — ошибки в целевом файле, но в
  программу `tsc` входят незакоммиченные файлы, которые могут быть их
  причиной; кандидат не сгорает.
- `conflict` — файл изменили снаружи во время проверки; MCP его не трогает.

Проверка видит незакоммиченные файлы разработчика, а коммит их не содержит.
Если такие файлы входят в программу `tsc`, успешный результат помечается
`validated_with_uncommitted` со списком файлов: raw-коммит может не
компилироваться без них. Если кто-то застейджит файл, пока идёт `tsc`, MCP
перед коммитом это заметит и вернёт `index_not_clean`, ничего не закоммитив.
Hook, который сам добавляет в индекс чужие файлы (например, `git add .`),
предотвратить без обхода hooks нельзя: это видно как `commit_scope_violation`.

Результат завершившегося `tsc` окончателен: повтор `candidate_apply` возвращает
сохранённый результат без нового запуска, а исправление — это новый кандидат и
новое ревью. Таймаут (300 с) или аварийное завершение `tsc` дают `error` с
откатом файла, и тот же кандидат можно применить снова.

После успешного typecheck MCP добавляет в индекс только целевой файл и создаёт
один локальный коммит `<commitType>: <первая строка objective, до 72 символов>` с trailer
`Stateful-Worker-Candidate: <candidateId>`. Git hooks работают как обычно и не
обходятся. Затем MCP проверяет, что коммит — единственный потомок прежнего HEAD
и содержит только целевой файл, и сравнивает закоммиченный файл с кандидатом:

- совпал — `committed`;
- hooks изменили файл — повторный typecheck; прошёл — `committed` с
  `hooksModified: true` и diff изменений hooks; не прошёл — `error`
  `hooks_broke_typecheck`, коммит остаётся в истории;
- hooks добавили другие файлы — `error` `commit_scope_violation`, коммит
  остаётся;
- hook отклонил коммит — `error` `commit_failed`, целевой файл снят с индекса
  и откатан, тот же кандидат можно применить снова.

История не переписывается: MCP не делает reset, amend и push. Повтор
`candidate_apply` после коммита возвращает сохранённый результат без нового
коммита. Фазы сохраняются в журнале. После аварии MCP при старте откатывает
свой незавершённый файл, только если HEAD не сдвинулся. Коммит с trailer этого
кандидата сохраняется, а чужой коммит или внешняя правка дают `conflict` без
изменения файлов. Проверка не повторяется автоматически. Репозиторию нужен хотя
бы один коммит.

`postprocess({ sessionId, packageDir? })` запускается после `committed` и только
прямо поверх raw-коммита, когда целевой файл не изменён, а индекс пуст (иначе
`conflict`). Другая незакоммиченная работа не мешает. Инструменты —
`eslint --fix` и `prettier --write` (порядок из `WORKER_POSTPROCESS`, по
умолчанию сначала eslint), запускаются без shell и только по путям raw-коммита.
Инструмент запускается, только если он объявлен в `dependencies` или
`devDependencies` в `package.json` пакета или его родителей до корня репо.
Версия неважна: те же аргументы работают в ESLint 8 и 9. Не объявлен — шаг
пропускается с `tool_skipped`; объявлен, но не установлен — `tool_not_found`.
npm-скрипты вроде `lint` MCP не запускает: это shell-команды, и обычно они
обрабатывают весь пакет, а не только файлы raw-коммита. Рабочий каталог и поиск
их бинарников — `packageDir`, по умолчанию каталог tsconfig из
`candidate_apply`. В монорепе это пакет, и ESLint находит свой конфиг оттуда.
Целевой файл должен лежать внутри `packageDir`, иначе `outside_package_dir`.
Затем повторный typecheck с тем же tsconfig:

- изменений нет — `no_changes`, коммита нет;
- typecheck прошёл — отдельный коммит `style: format <path>` с trailer
  `Stateful-Worker-Postprocess`, hooks работают как обычно; raw-коммит в
  истории не меняется;
- typecheck или инструмент упал — `failed`, файлы возвращены к raw-коммиту;
- инструмент тронул файлы вне raw-коммита — `error`
  `postprocess_scope_violation`, ничего не откатывается.

eslint с кодом 1 (исправил, но проблемы остались) не считается ошибкой: в
ответе будет `lint_problems_remain`. Файлы откатываются, только если в них всё
ещё результат форматирования, иначе `conflict`. Повтор после завершения
возвращает сохранённый результат. Сбой инструмента и отказ hook можно
повторить. После аварии действуют те же правила, что и для `candidate_apply`.

SQLite фиксирована в `<workspace>/.stateful-worker/state.sqlite`, содержит полные
исходники и тексты диалога; каталог исключён из Git. Одна DB обслуживается одним
MCP-процессом: второе соединение блокируется.
Во время inference эта сессия занята; после crash незавершённый ход помечается
`interrupted`, запрос автоматически не повторяется.

Окно корпоративной модели — 96K токенов; безопасный потолок входа по решению
пользователя — 64K. Оценка — консервативная эвристика `ceil(UTF-8 bytes / 3) + 256`,
а не точный tokenizer: warning 48000, hard input 64000, output reserve
`max_tokens: 8192`. Отдельный файл контекста или кандидат — не больше 192000 байт.
Проверки выполняются до чтения больших файлов и до inference; обрезания нет.
Ошибка оценки относительно tokenizer неизвестна. Реальный `usage` берётся
только из backend; отсутствующие input/output counts возвращаются как `null`.

Снимок читается через дескриптор, открытый только на чтение, с ограниченным
буфером и сравнением идентификатора файла без потери точности. Путь и время
изменения проверяются до/после чтения; при обнаруженной подмене контекст не
сохраняется. Это не атомарная проверка конечного пути средствами Windows;
механизм не рассчитан на намеренную подмену путей сторонними процессами.

Для разрешённой живой проверки, когда ключ уже есть в окружении:

```powershell
$env:WORKER_BASE_URL = 'https://localhost:8317/v1'
$env:WORKER_MODEL = 'gpt-6-luna'
npm run smoke:live
```

Эта команда вызывает модель через MCP stdio и выводит только безопасные
метаданные. Проверка на временной модели `gpt-6-luna` прошла.
Целевой Qwen3-Next ещё не проверен. Сервер не подставляет другую модель автоматически.

TLS проверяется с системным хранилищем CA. Подключение к корпоративному Kilo
описано в [инструкции](docs/setup/kilo.md). По результатам пользователя от
2026-10-13 корпоративный Kilo вызвал оба tools; `qwen2-5-coder-32b-instruct-awq`
ответила `READY`. По решению пользователя механика развивается локально с
`gpt-6-luna`; доступ и качество целевой Qwen3-Next проверяются отдельно при
deployment/пилоте и не блокируют I1.
