# Подключение MCP к корпоративному Kilo

Инструкция для разработчика, у которого уже установлен разрешённый
корпоративный Kilo Code и есть ключ разрешённого endpoint.
По принятой предпосылке корпоративный Kilo поддерживает все возможности
апстрима, включая MCP и формат кастомных ролей. Ограничения — выбор моделей
и отсутствие `webfetch`. По результатам пользователя от 2026-10-13 реальное
подключение MCP и вызовы обоих tools из Kilo работают на `qwen2-5-coder-32b-instruct-awq`.

1. В корне этого репозитория выполни `npm ci` и `npm run build`.
2. В настройках MCP корпоративного Kilo добавь локальный stdio-сервер.
   Команда — абсолютный путь к `node.exe`; аргументы — `--use-system-ca` и
   абсолютный путь к `dist/server.js`.
   Не используй `npm start` как MCP-команду: npm печатает служебный текст в stdout.
3. В личных настройках MCP Kilo задай `WORKER_BASE_URL`, `WORKER_MODEL` и
   `HARNESS_MODEL_API_KEY` через `env` из примера ниже. Замени `<API_KEY>` своим
   ключом только в этих настройках. Не записывай его в файлы проекта или `.kilocodemodes`.
4. Вызови `worker_diagnostics` с `{}`. При правильной конфигурации получишь
   `configured: true`; это ещё не доказательство доступности модели.
   Проверь `workspaceRoot`: это корень Git-репозитория, в котором Kilo
   запустил сервер, и именно с ним будут работать session tools. Если вместо
   него пришёл `workspaceError` или там не твой проект, Kilo запускает сервер
   не из каталога проекта. Тогда задай рабочий каталог процесса в настройках
   MCP. В апстримных конфигурациях это поле `cwd`; поддерживает ли его твоя
   сборка Kilo, не проверено.
5. Вызови `worker_instruct` с `{"message":"Reply with the single word READY."}`.
   Успех — `ok: true`, непустой `text`, `finishReason: "stop"`.
6. Проверь загрузку `.kilocodemodes`, видимость роли `qwen-test-supervisor`
   и разрешения `read`/`mcp` в корпоративном форке. Роль описывает будущий
   полный workflow; кандидаты и review доступны с I2, apply с проверкой
   компиляцией, raw commit и postprocess — с I3–I4.

Базовый JSON для настроек MCP в формате апстрима Kilo:

```json
{
  "mcpServers": {
    "stateful-coding-worker": {
      "command": "C:/nvm4w/nodejs/node.exe",
      "args": [
        "--use-system-ca",
        "S:/stateful-mcp/dist/server.js"
      ],
      "env": {
        "WORKER_BASE_URL": "https://localhost:8317/v1",
        "WORKER_MODEL": "gpt-6-luna",
        "WORKER_TSCONFIG": "tsconfig.json",
        "WORKER_POSTPROCESS": "prettier,eslint",
        "HARNESS_MODEL_API_KEY": "<API_KEY>"
      }
    }
  }
}
```

`<API_KEY>` — заполнитель, не настоящий ключ. Сервер ожидает переменную
`HARNESS_MODEL_API_KEY`; имя корпоративной переменной, из которой ты берёшь
ключ, может быть другим. Явное значение в `env` передаёт ключ MCP-процессу
без зависимости от наследования одноимённой переменной. Получение ключа и
вызов из Kilo подтверждены результатами пользователя от 2026-10-13.
Не вставляй ключ в этот документ или файлы проекта.

Тестовый адрес — `https://localhost:8317/v1`, временная модель — `gpt-6-luna`.
Реальная проверка `npm run smoke:live` через SDK stdio прошла с проверкой TLS.
Это не проверка конкретного корпоративного Kilo или целевой Qwen3-Next.

HTTP 401/403 означает отказ авторизации/доступа, 429 — ограничение запросов,
5xx — отказ backend. При ошибке TLS установи доверенный CA штатным способом
или передай путь к корпоративному CA через `NODE_EXTRA_CA_CERTS`.
Проверку TLS не отключай. MCP не выводит ключ, backend error body или prompt
в журналы; текст модели возвращается только вызывающему tool клиенту.

Обнаружение и вызовы обоих tools из корпоративного Kilo подтверждены
результатами пользователя от 2026-10-13. Пользователь разрешил локальную
разработку I1 с `gpt-6-luna`; целевая Qwen3-Next и проверка роли/permissions
остаются отдельными deployment/пилотными проверками.

Для I1 вызови `session_start` → `context_set` → `worker_chat` → `session_status`.
Корень проекта MCP вычисляет сам при запуске из своего рабочего каталога;
ни настройки, ни аргументы tools его не задают. SQLite создаётся в
`.stateful-worker/state.sqlite` под этим корнем и содержит полные исходники и
историю. Путь хранилища фиксирован;
symlink-пути запрещены, одна DB — один процесс.
Для чтения сохранённых данных после рестарта используй `session_status` с
`includeDetails: true`; обычный status не возвращает весь контекст.

## Проверка review loop (I2)

Сценарий выполняет роль `qwen-test-supervisor` в одном чате Kilo, без
копирования кода между чатами:

1. Роль согласует с разработчиком список тестовых сценариев. Затем
   `session_start` с одним путём `*.test.ts(x)` и `context_set` с исходником
   тестируемого модуля, брифом и готовым списком сценариев в
   `acceptanceCriteria`, по одному сценарию на пункт. Исполнитель реализует
   только этот список; изменить его можно новым `context_set`.
2. `worker_chat` с запросом на тесты. Успех — в ответе есть `candidateId` и
   `artifact` с полным кодом; роль ревьюит этот код сразу, без
   `candidate_read`. Если вместо них пришли `candidateDiagnostics`, модель
   нарушила формат; повтори `worker_chat` с уточнением.
3. `candidate_review` с `verdict: "reject"` и конкретными findings, включая
   пропущенные или лишние сценарии.
4. `worker_chat` ещё раз; новый кандидат должен учитывать findings.
5. Ревью кода из ответа, затем `candidate_review` с `verdict: "approve"`.
   `candidate_read` нужен только для diff, старых версий или после рестарта.
6. Проверь `session_status`: два кандидата, `phase: "approved"`. Рабочие
   файлы проекта, включая целевой тест, не изменены: запись делает только
   `candidate_apply`.

Локально механика этого цикла проверена на `gpt-6-luna`, где роль ревьюера
играл скрипт. Прохождение цикла в корпоративном Kilo с Qwen3.6 в роли
ревьюера ещё не проверено.

## Проверка apply, компиляции, raw commit и postprocess (I3–I4)

`WORKER_TSCONFIG` — путь относительно корня проекта к tsconfig,
в который попадают тестовые файлы. Если основной `tsconfig.json` исключает
`*.test.ts`, укажи отдельный конфиг для проверки тестов. Корень проекта
должен быть корнем Git-репозитория хотя бы с одним коммитом, а `typescript`
— установлен в проекте. Git identity (`user.name`, `user.email`) должна быть
настроена: MCP её не меняет.

1. Закоммить или убери свои изменения: при грязном рабочем дереве
   `candidate_apply` вернёт `conflict` и ничего не запишет.
2. После `candidate_review` с `approve` вызови `candidate_apply` с тем же
   `candidateId`. Успех — `status: "committed"`: в `git log` новый локальный
   коммит `test: add|update <path>` только с целевым файлом, `git status`
   чистый. Hooks репозитория при этом работают. Если они изменили файл, в
   ответе будут `hooksModified: true` и diff их изменений.
3. Отрицательный сценарий: одобри заведомо некомпилируемый кандидат.
   Ожидается `validation_failed` с ошибками `tsc`, файл возвращён к прежнему
   содержимому, `git status` чистый.
4. Передай ошибки компиляции в следующий `worker_chat`; новый кандидат снова
   проходит ревью и `candidate_review` перед `candidate_apply`.

5. После `committed` вызови `postprocess` с тем же `sessionId`.
   `WORKER_POSTPROCESS` перечисляет инструменты проекта в порядке запуска,
   например `prettier,eslint`; они должны быть установлены в проекте. Успех —
   `committed` с отдельным коммитом `style: format <path>` поверх raw-коммита
   либо `no_changes`, если форматировать нечего. Перед `postprocess` не делай
   своих коммитов: он работает только прямо поверх raw-коммита.

MCP не делает push: публикация коммитов — задача разработчика.
