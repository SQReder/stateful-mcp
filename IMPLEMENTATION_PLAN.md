# Implementation Plan — Stateful Qwen Coding Worker

**Статус:** механика I0 принята пользователем; I1 реализован и проверен локально на `gpt-6-luna` (10 затронутых тестов после исправлений по ревью, три хода и рестарт через MCP). Корпоративный Kilo transport подтверждён результатами пользователя от 2026-10-13 на `qwen2-5-coder-32b-instruct-awq`. Целевая Qwen3-Next отложена до deployment/пилота. Механика I2 реализована и проверена локально (30 тестов, живой review loop на `gpt-6-luna`); корпоративный review loop с Qwen3.6 не проверен. Механика I3 реализована и проверена локально (реальный `tsc` во временных Git-репозиториях). Механика I4 (raw commit и postprocess) реализована и проверена локально (50 тестов, фейковые prettier/eslint); I5–I6 не начаты. Бюджет входа — 64K из окна 96K по решению пользователя.
**Основа:** [BASELINE.md](./BASELINE.md), v0.2.  
**Пилот:** тесты Vitest для существующего TypeScript-модуля.  
**Архитектура:** универсальный stateful MCP Coding Worker (Qwen3-Next-80B-A3B-Instruct) + специализированная роль [Qwen Test Supervisor](./.kilocodemodes) (Qwen3.6) в разрешённом корпоративном Kilo Code.

## 1. Цель и ограничения

Получить интерактивный диалог: Qwen3.6 собирает бриф и исходники → Qwen3-Next через MCP создаёт кандидат → Qwen3.6 ревьюит и возвращает feedback → **только одобренный** кандидат временно применяется → проходит компиляцию → создаётся raw commit → форматирование затронутых файлов и отдельный postprocess commit

Два разных feedback loop:
1. **Review loop до записи файлов:** несколько кандидатов в одной stateful-сессии; reject → feedback → новая версия; Qwen3.6 не обязана применять код для ревью.
2. **Validation loop после approval:** apply → typecheck/compile; FAIL → безопасное восстановление → диагностика Qwen3.6 → новая генерация → **новое ревью** до повторного apply.

Инварианты:
- Нет другого LLM-харнесса; только корпоративный Kilo + самописный MCP.
- Qwen3-Next — instruct/chat **без tool calls**, файловой системы, Git и shell.
- MCP универсален по назначению; тест-дизайн находится в роли Qwen Test Supervisor. В пилоте ограничение на **один полный тестовый файл**.
- Гейты MCP детерминированы; инженерные решения, acceptance и семантический feedback принадлежат Qwen3.6/разработчику.
- Raw commit сохраняется в истории, без reset/squash. Только компилируемый результат; ESLint/Prettier после него.
- Не допускать запись/перезапись файлов вне allowedPaths и уничтожение внешних изменений.
- **Граница ответственности:** MCP создаёт и сохраняет локальные коммиты, но **не выполняет push, не проверяет remote и не управляет публикацией**. Публикация — ответственность разработчика. Корпоративный KPI считает закоммиченный и запушенный код, но измерение KPI находится вне MCP.

## 2. Порядок реализации

Последовательность: **I0 → I1 → I2 → I3 → I4 → I5 → I6**. Следующий этап начинается после закрытия своего gate; отдельно фиксируем открытые риски. Механические сценарии тестируем через fake LLM и временные репозитории, реальные inference — в отдельных интеграционных тестах.

### I0 — MCP skeleton и connectivity

**Результат:** корпоративный Kilo вызывает локальный MCP, а он делает одиночный запрос к Qwen3-Next.

**Реализация:**
- Каркас MCP-сервера на TypeScript, stdio transport, конфигурация endpoint.
- Диагностический tool и простой instruct/chat запрос без tool calls.
- Таймауты, понятные ошибки подключения/авторизации/ответа; без секретов или целого контекста в логах.
- Проверка реального обнаружения/вызова MCP и передачи ключа из корпоративного Kilo; форматы MCP и кастомной роли принимаются как в апстриме.

**Gate I0 — CONNECTED (механика; принята пользователем 2026-10-13)**
- [x] Kilo обнаруживает и вызывает MCP tool; передача ключа подтверждена результатами пользователя от 2026-10-13.
- [x] Разрешённая локальная модель `gpt-6-luna` отвечает через MCP; целевой Qwen проверяется отдельно при deployment/пилоте по решению пользователя.
- [x] Timeout, 401/403/429/5xx и malformed response возвращают диагностику без падения MCP (fake backend и stdio tests).
- [x] Нет второго LLM-харнесса.

Локальные доказательства: `npm run typecheck` и `npm test` — exit 0, 17 тестов;
`npm run smoke:live` — exit 0 через stdio, HTTPS с проверкой TLS,
временная `gpt-6-luna`.

Результаты реального Kilo MCP smoke, предоставленные пользователем 2026-10-13
(не собственная проверка агента):
- `worker_diagnostics`: `configured: true`, `model: qwen2-5-coder-32b-instruct-awq`, `timeoutMs: 60000`, `stage: I0`.
- `worker_instruct`: `ok: true`, `text: READY`, `finishReason: stop`.

Эта модель не подтверждает целевую Qwen3-Next. Пользователь разрешил продолжить
I1 с локальной `gpt-6-luna`: корпоративные модели недоступны с dev-машины.
Доступ/качество целевого Qwen и загрузка роли/permissions остаются deployment/пилотными проверками.

### I1 — stateful session и управляемый контекст

**Результат:** диалог и снапшоты исходников переживают перезапуск MCP; каждый inference получает только выбранный рабочий контекст.

**Реализация:**
- Инструменты `session_start`, `context_set`, `worker_chat`, `session_status`.
- Постоянное хранилище (например, SQLite): sessionId, brief, turns, snapshots, contextRevision, ошибки.
- Чтение файлов по workspace-relative путям; снимки содержимого и hashes.
- Разделение **хранимой полной истории** и **собираемого prompt**: не реплеить всё подряд, не копить все версии кода в inference.
- Явная консервативная оценка `ceil(UTF-8 bytes / 3) + 256`, warning 48K, hard input 64K при окне 96K (решение пользователя 2026-10-13 вместо стартовых 32K, где байт считался токеном), output reserve 8192; `max_tokens` проверен на локальном endpoint. Это не точный tokenizer, ошибка оценки неизвестна; реальные usage counts отдельные и nullable, без silent truncation.
- Один `worker_chat` = ровно один inference, без записи исходников.

**Gate I1 — SESSION DURABLE**
- [x] Три последовательных хода в одной сессии; контекст обновляется по явному `context_set`.
- [x] После рестарта доступны brief, снимки, turns и revision (полный `session_status` только с `includeDetails: true`).
- [x] Превышение оценочного бюджета явно блокируется до inference; большие файлы проверяются до чтения.
- [x] Две сессии не смешивают данные; исходники остаются неизменными.

До ревью `npm test` — exit 0, 24 теста. Проверки после исправлений по ревью:
`npm run build`, `node --test tests/sessions.test.mjs tests/mcp.test.mjs`
и `npm run typecheck` — exit 0, 10 затронутых тестов. Предыдущий live MCP smoke
на `gpt-6-luna` — три успешных хода, revision 2, рестарт и неизменность исходника.
SQLite exclusive lock, symlink boundaries и crash recovery без replay покрыты тестами.

### I2 — кандидаты и review loop (первая полезная демонстрация)

**Результат:** Qwen3.6 получает версии кода с diff, одобряет или отклоняет без изменения рабочих файлов.

**Реализация:**
- Извлечение и хранение **неизменяемого кандидата** с candidateId, content, contextRevision.
- `candidate_read` возвращает полный код и diff, не резюме исполнителя.
- `candidate_review(approve | reject)` с findings; approval привязан к конкретному immutable кандидату и актуальной revision.
- Reject превращается в feedback для следующего `worker_chat` в **той же** логической сессии.
- Пилот: один полный `*.test.ts(x)` файл вместо patch; базовый MCP-контракт не завязан на Vitest.
- Обрезанный inference output, неправильный artifact path или некорректный ответ не становятся валидным кандидатом.

**Gate I2 — REVIEW WITHOUT SIDE EFFECTS**
- [x] Два или больше кандидата в одной сессии, все версии и findings доступны после рестарта.
- [x] Reject не мутирует старую версию; approve проверяет revision.
- [ ] Qwen3.6 ревьюит реальный код и diff.
- [x] До вызова apply рабочее дерево не меняется.
- [ ] Цикл проходит через Kilo без ручного копирования между чатами.

Локальные доказательства: `npm run typecheck` и `npm test` — exit 0, 30 тестов.
Разовая живая проверка через MCP stdio и HTTPS на `gpt-6-luna`: два кандидата,
reject → feedback → approve, рестарт, исходник и целевой файл не изменены.
Ревьюером в ней был скрипт, а не Qwen3.6; это проверка механики, не качества
тестов. Оставшиеся два пункта проверяются в корпоративном Kilo
(сценарий — в [инструкции](docs/setup/kilo.md)).

**Checkpoint:** после I2 уже можно проверить центральную гипотезу — способна ли Qwen3-Next улучшать тесты по замечаниям Qwen3.6.

### I3 — безопасный apply и validation loop

**Результат:** одобренный кандидат проверяется на реальном проекте; при ошибке компиляции не оставляет чужих или своих неконтролируемых изменений.

**Реализация:**
- `candidate_apply` проверяет approval, revision, исходные hashes, неизменённый целевой файл и пустой index (другая незакоммиченная работа допустима — решение пользователя 2026-10-13) и границы allowedPaths.
- Защита от path traversal и symlinks; запрет модификаций вне workspace.
- Журнал фаз `applying → validating → validated` для безопасного рестарта.
- Резервная копия исходного содержимого; временная запись только разрешённого файла.
- Доверенная проверка compilation/typecheck, которая **включает тестовые файлы** и не переписывает исходники.
- FAIL: возвращение диагностик (exit code, stderr, stdout), безопасное восстановление; при внешних правках — `conflict` вместо насильственного отката.
- После ошибок новый кандидат снова обязан пройти review loop; MCP не генерирует исправления сам.

**Gate I3 — SAFE APPLY**
- [x] Корректный кандидат проходит настроенную компиляцию.
- [x] Намеренно сломанный кандидат даёт диагностику и оставляет проект в прежнем состоянии.
- [x] Коммитов при FAIL нет; исправленный кандидат проходит новое ревью.
- [x] Несанкционированные пути, stale snapshots и чужие изменения блокируются.
- [x] Crash в середине apply позволяет восстановиться/остановиться без потери чужих правок.

Локальные доказательства: `npm run typecheck` и `npm test` — exit 0, 37 тестов;
реальный `tsc` 7.0.2 во временных Git-репозиториях с `incremental: true`
доказывает отсутствие побочных записей при проверке. Crash проверен через
сохранённую фазу журнала, а не через реальное падение процесса. Независимое
ревью I3 проведено, подтверждённые замечания исправлены. На реальном модуле
и из корпоративного Kilo apply ещё не проверялся. На I3 успех завершался
статусом `validated`; с I4 его заменил `committed`.

### I4 — raw Git commit и postprocess

**Результат:** сохранён исходный компилируемый код Qwen3-Next; formatter/linter работают только с изменёнными файлами и их изменения видны отдельно.

**Реализация:**
- После успешного G5 создать `git commit` с обязательными Git hooks; stage **только allowed files**, без `git add -A`.
- Hooks не обходить. Решение пользователя 2026-10-13: если hooks изменили закоммиченный файл, повторить typecheck; успех — `committed` с `hooksModified` и diff, провал — ошибка `hooks_broke_typecheck`, коммит остаётся в истории.
- Внутренне сохранить commit metadata и список изменённых файлов; **публичному MCP API SHA не нужен**.
- Реализовать `postprocess`: только пути raw-коммита, доверенные Prettier/ESLint fix, затем повторный typecheck.
- При наличии изменений — отдельный postprocess commit; если изменений нет — `no_changes`.
- При postprocess FAIL raw commit остаётся в истории, отдельный коммит не создаётся; восстановление только при отсутствии конфликта.
- Идемпотентность повторного `candidate_apply`/`postprocess`; восстановление между Git-операциями; не делать reset/squash/force push.
- Итог MCP — локальная история с raw commit и, если потребовалось, postprocess commit. На этом управление Git завершается: ни push, ни проверок remote refs, ни publication status в MCP.

**Gate I4 — HISTORY PRESERVED**
- [x] Некомпилируемый кандидат не создаёт raw commit.
- [x] Компилируемая исходная генерация фиксируется **до** auto-fix.
- [x] Отдельный postprocess commit появляется только после успешного повторного typecheck и только при реальных изменениях.
- [x] Неизменённые и посторонние файлы не попадают в коммиты (MCP индексирует только целевой файл и пути raw-коммита; исключение — ниже).
- [x] При ошибке форматтера raw commit сохранён, чужие правки целы.
- [x] Повторные tool calls не создают дубликатов коммитов.
- [x] MCP не делает push, не опрашивает remote и не сообщает статус публикации.

Локальные доказательства: `npm run typecheck` и `npm test` — exit 0, 50 тестов на
реальных временных Git-репозиториях с hooks и реальным `tsc`. Hook, который
сам добавил в коммит другой файл, нельзя предотвратить без обхода hooks: MCP
сообщает `commit_scope_violation` и не переписывает историю. Повторы
`candidate_apply`/`postprocess` и восстановление после краша не создают второй
коммит. Независимые ревью raw commit и postprocess проведены, подтверждённые
замечания исправлены. Prettier и ESLint в тестах — фейковые CLI; с настоящими
инструментами и в корпоративном Kilo этап не проверялся.

### I5 — end-to-end через Qwen Test Supervisor

**Результат:** разработчик проходит полный сценарий в Kilo: тест-дизайн → генерация → review loop → apply → validation loop → commits.

**Реализация:**
- Подключить инструменты MCP к роли `qwen-test-supervisor`; проверить permissions корпоративного форка.
- Проверить, что Qwen3.6 не пишет код напрямую через edit/command в обход MCP.
- Пройти успешный сценарий и два отрицательных: reject при review, compile fail после apply.
- Роль сообщает пользователю только фактически выполненные проверки, изменения и состояние Git.

**Gate I5 — E2E FROM KILO**
- [ ] Цикл работает без копирования исходников/ответов между чатами.
- [ ] Оба feedback loop реально выполнены на пилотном модуле.
- [ ] У Qwen3-Next нет tool calls и прямого доступа к проекту.
- [ ] Журнал MCP, результаты компиляции и итоговый Git совпадают с отчётом роли.
- [ ] После локальных коммитов MCP завершает workflow без попыток публикации.

### I6 — реальный пилот и стабилизация

**Результат:** есть данные для решения, продолжать ли эксперимент и расширять ли MCP на другие типы задач.

**Реализация:**
- 5–10 настоящих TS-модулей различной сложности.
- Замерять turns, input/output tokens, число review/compile iterations, время до принятия, потребность в ручных исправлениях, качество assertions/регрессий.
- Измерить эффективность генерации и качество результата отдельно от корпоративного KPI. Доставка коммитов в remote и проверка KPI не входят в пилотную функциональность MCP.
- Прогнать отказы: timeout, 429/500, malformed output, рестарт MCP, stale context, конфликт Git, ошибка formatter.
- По итогам решить **go / iterate / stop**. До этого не обобщать API под многофайловые фичи.

**Gate I6 — PILOT REVIEWED**
- [ ] По каждому модулю сохранены условия задачи, итерации, проверенные результаты.
- [ ] Ноль потерь чужого кода, выходов за scope и некомпилируемых raw-коммитов.
- [ ] Отказы воспроизведены и безопасно обработаны.
- [ ] Человек оценил полезность тестов; компиляция сама по себе не считается доказательством качества.
- [ ] Результаты оценки качества и времени зафиксированы; есть решение о развитии проекта. MCP не требует сведений о публикации.

## 3. Runtime gates на каждый кандидат

Эти проверки MCP обязан применять независимо от поведения Qwen3.6.

| Gate | Условие перехода | Неуспех |
|---|---|---|
| **G1 Context Ready** | brief + snapshots + revision + token budget валидны | Нет inference; исправить контекст |
| **G2 Candidate Ready** | Ответ полон; artifact извлечён и лежит в allowedPaths | Нет кандидата для approval |
| **G3 Review Approved** | Одобрен именно этот immutable candidate на текущей revision | Нет apply; feedback в review loop |
| **G4 Apply Safe** | Чистый index/worktree, файлы актуальны, path scope безопасен | `conflict`, никаких записей |
| **G5 Compilation Passed** | Временно применённый код прошёл обязательный typecheck/compile | Восстановление, диагностика, новый candidate → G3 |
| **G6 Raw Committed** | Только принятая генерация закоммичена до auto-fix | Не запускать postprocess; вернуть Git-ошибку |
| **G7 Postprocess Validated** | Formatter/linter не вышли за raw paths; повторный typecheck успешен | Не коммитить postprocess; сохранить raw commit |

**G3 семантический и принадлежит Qwen3.6.** Остальные в основном детерминированные и должны быть реализованы техническими предусловиями, а не только текстом роли.

## 4. Тестовая стратегия MCP

Использовать fake LLM для стабильных тестов, реальные модельные вызовы — отдельно. Git-тесты проводить в disposable репозиториях.

| Область | Набор проверок |
|---|---|
| Transport/API | discovery из Kilo, аргументы, ошибки backend, timeout |
| Session/context | restart, snapshots, token budget, разные сессии, отсутствие silent truncation |
| Candidates/review | immutable versions, неправильный формат ответа, truncated output, stale approval |
| Apply | allowedPaths, symlinks, конфликт, clean working tree, crash recovery |
| Validation | PASS/FAIL компиляции, реальные `*.test.ts(x)` внутри typecheck |
| Git | scoped staging, два коммита, no-op postprocess, двойные вызовы, отсутствие reset/squash |
| Postprocess | файлы только из raw commit, regression после auto-fix, сохранение raw на FAIL |
| E2E | живой диалог Kilo/Qwen3.6 ↔ MCP/Qwen3-Next, реальный пилот |

Критические отказные сценарии, которые обязательно включить в автоматические проверки:
1. Одобрен `c3`, а к применению пришёл `c4`: **запретить**.
2. MCP упал после записи файла, но до компиляции: после рестарта **не потерять** исходное состояние.
3. ESLint изменил компилируемый raw-код так, что typecheck упал: **нет второго коммита**, raw остаётся.
4. Внешняя правка появилась между snapshot и apply: **conflict**, а не принудительный overwrite.

## 5. Definition of Done

- **Первый полезный checkpoint (I2):** работающий многотуровый диалог с версионированными кандидатами и ревью без изменения проекта.
- **Технический MVP (I5):** весь сценарий в Kilo с review, компиляцией, сохранённым raw commit и scoped postprocess; без публикации.
